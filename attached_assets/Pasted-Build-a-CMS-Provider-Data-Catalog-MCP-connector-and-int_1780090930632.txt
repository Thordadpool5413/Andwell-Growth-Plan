Build a CMS Provider Data Catalog MCP connector and integrate it into the Andwell competitive intelligence application.

Purpose

The application must use the CMS Provider Data Catalog API as the official public data source for Medicare certified hospice and Medicare certified home health provider verification.

The CMS API is the data source.

The MCP server is the tool layer that allows the app AI to safely access, query, normalize, cache, compare, and cite CMS provider data.

The MCP connector must be built as a real working integration, not a visual placeholder.

Core objective

Create an MCP server that exposes CMS Provider Data Catalog data to the Andwell app through structured tools.

The MCP tools must allow the app to:

1. Discover CMS hospice and home health datasets
2. Retrieve CMS dataset metadata
3. Query provider records
4. Filter providers by Maine
5. Filter providers by hospice
6. Filter providers by home health
7. Match CMS provider records to Andwell competitors
8. Normalize provider names and aliases
9. Verify Medicare provider status
10. Pull quality and experience data when available
11. Pull location data when available
12. Pull service area or zip level data when available
13. Store CMS evidence in the app database
14. Attach CMS evidence to competitor profiles
15. Refresh CMS data on a schedule
16. Flag stale or missing data
17. Return clean structured results to the app front end

Important distinction

Do not treat competitor websites as the primary verification source for Medicare status.

Competitor websites may describe services.

CMS data verifies whether the provider exists in the Medicare provider universe.

For Medicare Part A hospice competitor verification, CMS data must be treated as a higher trust source than competitor websites.

For Medicare certified home health verification, CMS data must be treated as a higher trust source than competitor websites.

Required CMS data scope

The MCP connector must support the following CMS Provider Data Catalog topic areas.

1. Hospice care

Use this topic to identify and verify Medicare certified hospice providers, hospice provider identity, hospice location data, hospice quality data, hospice CAHPS data when available, hospice state data, hospice national data, and hospice service area or zip data when available.

2. Home health services

Use this topic to identify and verify Medicare certified home health agencies, home health provider identity, provider location data, home health quality data, HHCAHPS data when available, state data, national data, and service related measures when available.

3. Medicare post acute care and hospice public use data when available

Use this area for deeper utilization and payment intelligence when the app needs Medicare post acute or hospice level utilization, payment, charge, provider, state, or national level analysis.

MCP tool requirements

Create the following MCP tools.

1. search_cms_provider_datasets

Purpose:
Search the CMS Provider Data Catalog for hospice and home health datasets.

Input:
Topic, keyword, provider type, and optional state.

Output:
Dataset title, dataset identifier, description, topic, modified date, release date, planned update date, data dictionary reference, API reference, and confidence score.

2. get_cms_dataset_metadata

Purpose:
Retrieve metadata and column definitions for a selected CMS dataset.

Input:
Dataset identifier.

Output:
Dataset title, description, available columns, data types, update dates, source information, and usable query fields.

3. query_cms_dataset

Purpose:
Query a CMS dataset with filters, pagination, and selected columns.

Input:
Dataset identifier, filters, selected columns, limit, offset, sort field, and sort direction.

Output:
Rows, total count when available, pagination information, query metadata, and source reference.

4. fetch_maine_hospice_providers

Purpose:
Return hospice provider records for Maine.

Input:
Optional provider name, city, county when available, zip code, parent company, and active status.

Output:
Hospice provider records including provider name, CMS certification number when available, address, city, state, zip code, phone when available, quality fields when available, CAHPS fields when available, and source evidence.

5. fetch_maine_home_health_agencies

Purpose:
Return Medicare certified home health agency records for Maine.

Input:
Optional provider name, city, county when available, zip code, parent company, and active status.

Output:
Home health provider records including provider name, CMS certification number when available, address, city, state, zip code, phone when available, quality fields when available, HHCAHPS fields when available, and source evidence.

6. match_competitor_to_cms_provider

Purpose:
Match a competitor from the Andwell app to CMS hospice or home health provider records.

Input:
Competitor name, aliases, parent company, city, state, zip code, provider type, and known website.

Output:
Best match, possible matches, match confidence, name similarity, location similarity, provider type match, CMS evidence, and recommended verification status.

7. normalize_provider_identity

Purpose:
Normalize provider names, parent company names, aliases, legacy names, and brand variants.

Input:
Raw provider name, aliases, parent organization, and source text.

Output:
Normalized provider name, display name, known aliases, likely parent company, legacy names, and duplicate risk.

8. sync_cms_provider_data

Purpose:
Refresh CMS hospice and home health datasets into the local app database.

Input:
Dataset identifiers, provider type, state, sync mode, and date range when available.

Output:
Records created, records updated, records unchanged, records archived, failed records, sync timestamp, and error details.

9. get_provider_quality_snapshot

Purpose:
Retrieve quality and patient experience data for a matched provider when available.

Input:
Provider identifier, provider type, CMS certification number when available, and dataset references.

Output:
Quality measures, patient experience measures, state benchmarks when available, national benchmarks when available, reporting period, and source evidence.

10. get_provider_service_area_snapshot

Purpose:
Retrieve service area or zip level information for hospice or home health providers when available.

Input:
Provider identifier, provider type, CMS certification number when available, state, and zip code.

Output:
Provider service area data, zip level data when available, state, city, county when derivable, and confidence score.

MCP behavior requirements

The MCP server must be read only for CMS data.

The MCP server must never modify CMS data.

The MCP server may cache CMS data in the local app database for performance and auditability.

The MCP server must support pagination because CMS datasets may return records in limited batches.

The MCP server must handle empty responses gracefully.

The MCP server must handle renamed datasets gracefully.

The MCP server must handle missing columns gracefully.

The MCP server must map columns dynamically from metadata instead of assuming every CMS dataset has the same schema.

The MCP server must log every CMS query used to support a material claim.

The MCP server must return evidence in a format the app can attach to approved claims and competitor profiles.

For each seeded competitor, call match_competitor_to_cms_provider.

If a confident CMS match exists, mark the competitor as CMS Verified.

If multiple possible matches exist, mark the competitor as Needs Review.

If no CMS match exists, mark the competitor as Not Verified by CMS and keep the competitor in the seeded reference set.

Do not delete seeded competitors automatically.

Do not assume that no match means the organization does not exist.

No match means no CMS match was found using the current dataset, query logic, and available aliases.

Evidence hierarchy

When classifying Medicare hospice or home health competitors, use this evidence hierarchy.

1. CMS Provider Data Catalog records
2. Maine state licensing or certification sources
3. Medicare Care Compare related public data
4. Competitor website
5. User uploaded documents
6. AI inference

AI inference alone cannot verify Medicare status.

Competitor website claims alone can support service description, but CMS or state data should verify Medicare provider status when possible.

Security and reliability requirements

The CMS MCP connector must be server side only.

Do not expose raw internal API credentials if future credentials are added.

Do not expose unnecessary CMS query internals to the public front end.

Validate all user inputs before passing them to CMS query functions.

Prevent query injection in SQL style CMS queries.

Use safe query builders or parameterized query construction where possible.

Set request timeouts.

Use retry logic for temporary CMS errors.

Cache successful responses.

Log failures without crashing the app.

Show the user a clear error if CMS data cannot be reached.

Never fake CMS results.
